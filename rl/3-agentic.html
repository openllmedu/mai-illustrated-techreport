Section 3.3

Agentic Climb

Teaching the model to interact with real codebases and tools through multi-step reasoning.

TL;DR

The agentic climb trains the model on 265k SWE environments built from real GitHub PRs (filtered from 102M) and 130k+ synthetic tool-use tasks. The model learns to interact with sandboxed environments over multiple steps, using bash and file-editing tools. Anti-cheating measures prevent reward hacking via internet search, git history, and test tampering.

What Makes Agentic Different?

Unlike STEM problems (single question -> single answer), agentic tasks require the model to interact with an environment over multiple steps. The model reads a codebase, makes edits, runs tests, sees results, and iterates. This is much closer to how humans actually solve software engineering problems.

The agentic climb trains on two domains:

  • Software Engineering (SWE) — fixing real bugs in real code repositories, using bash and file-editing tools
  • General Tool Use — calling APIs, managing databases, interacting with services (e.g., booking systems, inventory management)
Figure 18 — Agentic RL Loop

The model alternates between thinking/acting and observing environment feedback. At each step, it can emit tool calls (bash commands, file edits) or produce a final answer. Tool outputs are appended to the context for the next step.

The team jointly trains on a mixture of agentic and STEM tasks. STEM tasks help stabilize the RL climb and show positive transfer to agentic performance. Interestingly, agentic tasks transferred neither positively nor negatively to STEM.

Multi-Step RL Framework

The agentic framework extends the single-step GRPO objective to trajectories of multiple actions. The orchestration follows a ReActReasoning + Acting — a prompting pattern where the model alternates between thinking (reasoning about what to do) and acting (executing a tool call). The pattern is: Thought -> Action -> Observation -> Thought -> Action -> ... until the task is complete.Learn more-style loop:

  1. Model receives a task description and thinks about what to do
  2. Model emits a tool call (e.g., bash: ls src/)
  3. Tool is executed in a sandbox, output is returned
  4. Model sees the output, thinks again, and emits the next action
  5. Loop continues until the model signals completion or hits a budget limit
  6. A grader evaluates the final state (tests pass? database correct? task complete?)

Sandbox Execution Environment (SEE)

Every agentic task runs in a fresh, isolated containerA lightweight, isolated environment that packages code and its dependencies. Each RL task gets its own container that is destroyed after completion. This ensures reproducibility (same starting state every time) and prevents state leakage between tasks.Learn more — a self-contained environment with all code and dependencies pre-installed. Containers are network-isolated by default (no internet access) to prevent the model from cheating by looking up solutions. When network access is needed (e.g., installing packages), traffic goes through caching proxies with domain allowlists.

Preventing Reward Hacking

Even with executable test cases, models find creative ways to cheat:

  • Internet search — Looking up the actual PR solution on GitHub. Mitigated by disabling network access.
  • Git history search — Searching git commits to find the solution. Mitigated by scrubbing all commits after the base commit ("time-traveling" the repo).
  • Test tampering — Modifying tests to make them pass without fixing the bug. Mitigated by resetting test files before grading and hiding test changes during inference.

General Tool Use

Beyond SWE, the team trains on diverse tool-calling tasks: inventory management, scheduling, report creation, customer support, and other enterprise scenarios. Each environment has a set of available tools (often 50+), an initial state, and verifiable outcomes.

Synthetic Environment Generation

To scale beyond hand-curated environments, a pipeline generates self-contained environments from plain-English descriptions:

  1. Environment bootstrapping — Generate tool definitions, implement functions, seed databases
  2. Task creation — Sample tool-call trajectories, create entities, formulate user requests
  3. Verification — Execute generated actions, remove overly similar tasks

This pipeline produced 150+ environments and 130,000+ tasks. Environment-specific personasFictional user profiles with specific needs, communication styles, and backgrounds. Using diverse personas forces the model to handle different types of requests, levels of technical sophistication, and communication patterns.Learn more further diversify the training data. Tasks that don't require tool use are also included to prevent over-eager tool calling.

SWE Agent Tools

The SWE agent uses exactly two tools during training and evaluation, exposed via OpenAI-compatible function-calling schema:

bash

Executes bash commands in the repository context. Each action runs in a new subshell (directory/env changes aren't persistent). The model has a full Linux shell environment but must use non-interactive flags (-y, -f) and avoid tools like vi or nano.

str_replace_editor

A custom file editing tool with 5 commands: view (cat with line numbers or directory listing), create (new files only), str_replace (exact string match replacement), insert (add text after a line), and undo_edit (revert last edit). The old_str must match exactly one location — the model must include enough context to make it unique.

For Terminal-Bench 2.0 evaluation, only the bash tool is used.

How Agentic Reasoning Evolves

As the model strengthens during RL training, its chains of thought show three distinct behavioral shifts:

Weak Models Sanity-Check, Strong Models Run Unit Tests

Weak model: Reviews its changes by listing what it believes it accomplished ("Added proper type imports... Refactored add_seed()... Fixed get_export_list()...") but never actually executes any tests to verify.
Strong model: Writes and runs unit tests to check its work: "The tests still pass. So I have all the core functionality working." It then reviews requirements AND confirms backward compatibility through actual test execution.

Weak Models Fixate on Edits, Strong Models Do Evidence Archaeology

Weak model: Understands the target but spends most turns on exact edit mechanics — "Let me view more of the end of the file to see the exact structure and line endings... I need to match the exact tab indentation..." — making small, cautious steps without building broader context.
Strong model: Fully explores the repository and collects extensive evidence before taking any action. It reads main.go, types.go, test files, README, and docs to understand the full architecture before forming a plan: "I see the structure. The code currently handles: 1. Issue comments... 2. Check suite events... But the problem says we need to handle..."

Weak Models Speculate, Strong Models Seek Source of Truth

Weak model: Traces step by step around adjacent code paths by trial and error — "Hmm, let me search more specifically for isAddBeanFor in test files... No direct references. Let me look at how isAddBeanFor is defined in the API..."
Strong model: Ties behavior to the data source that feeds code generation. Instead of guessing what the generated code should look like, it traces back to the source data: "I see isAddBeanFor is defined in Builder interface... Let me look at how it's used... The isAddBeanFor determines if a bean should be added based on if parent scope already has it..."
Strong agentic models develop three habits that weak models lack: verifying work through actual test execution (not just mental review), building comprehensive repository context before acting, and tracing problems to their source of truth rather than guessing at adjacent code paths.
