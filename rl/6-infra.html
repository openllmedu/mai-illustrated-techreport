RL Infrastructure

Rocket: the custom framework that runs asynchronous RL across thousands of GPUs.

TL;DR

Rocket is a custom async RL framework using YOLO for training and SGLang for inference. The largest job used 4,864 GPUs (5:1 inference-to-training ratio). Key challenges: inference throughput optimization (prefix caching hits 97-98%), system stability at scale (defense-in-depth across 3 layers), and the numerics gap between training and inference (solved with BF16 + routing/mask replay).

Rocket: Large-Scale Async RL

Training MAI-Thinking-1 via RL required infrastructure that didn't exist in any open-source framework. The team built Rocket, an in-house framework for asynchronous distributed RL that scales across thousands of GPUs.

Figure 19 — Rocket Architecture

Rocket's data flow: a Controller distributes tasks to Problem Workers, which request rollouts from Rollout Workers. Rollout Workers interact with SGLang inference servers. Completed, graded rollouts flow back through the controller to the YOLO learner for gradient updates.

The largest RL job used 4,864 GB300 chips: 4,096 for inference and 768 for training (the "learner"). That's roughly a 5:1 ratio of inference to training GPUs — generating 128 responses per problem is far more compute-intensive than the gradient update.

The Four Components

Controller

Loads RL tasks, distributes them to problem workers, receives graded rollouts, filters them, and sends batches to the learner. Supports both on-policy (fresh model for each batch) and off-policy (allowing some staleness for throughput).

Problem Worker

Manages the lifecycle of a single task: sends rollout requests, applies early-exit and pass-rate filters, computes advantagesThe normalized reward for each rollout within its group. Computed as (reward - group_mean) / group_std. Positive advantage means the response was better than average; negative means worse.Learn more for each rollout, and returns results. Handles fault tolerance (retrying failed rollouts).

Rollout Worker

Generates a single rollout: sends prompts to inference servers, parses responses, dispatches tool calls (for agentic tasks), and optionally grades the result. For agentic tasks, this involves a multi-step loop of inference -> tool execution -> inference.

Router & Inference

Built on SGLangA fast LLM serving engine that provides high-throughput inference with features like prefix caching, continuous batching, and radix attention. Used for generating rollouts during RL training. The SGLang router handles load balancing and fault tolerance across multiple server replicas.Learn more. The router handles load balancing, traffic control, and prefix caching. For multi-turn workloads, prefix cache hit rates reach 97-98%.

Inference Optimization

Since inference uses 5x more GPUs than training, optimizing inference throughput is critical:

  • Single-turn (STEM): Short prompts but up to 128k-token generations. Bottleneck is KV cacheKey-Value cache — stores the intermediate attention computations for all previously generated tokens. Without it, the model would need to recompute attention over the entire sequence for each new token. The cache grows linearly with sequence length and can consume enormous GPU memory at 128k tokens.Learn more memory. Reduced via expert parallelism and data parallelism for attention.
  • Multi-turn (agentic): Long prompts (growing with each step) but short generations. Bottleneck is prefillThe initial computation where the model processes all input tokens in parallel before generating. For agentic tasks with long contexts, prefill is the bottleneck. Prefix caching avoids re-prefilling the parts of the context that haven't changed between turns.Learn more. Mitigated by prefix caching (97-98% hit rate).

System Stability

At 4,000+ GPU scale, individual machines crash, hang, and slow down regularly. Rocket uses defense-in-depth at three layers:

  1. Replica level — Each SGLang server runs a self-watchdog that monitors its own health. Unhealthy replicas trigger graceful restarts.
  2. Router level — Acts as a circuit breaker: stops admitting requests to unhealthy replicas, probes before reopening, and rediscovers replicas that silently dropped out.
  3. Job level — A liveness monitor tracks live actors in each class. Falls below threshold? Clean restart. A step-progress watchdog catches the harder case where everything appears alive but training has stopped advancing.

Individual replica failures degrade pool throughput but never lose rollouts — failed requests are retried against other replicas.

The Numerics Gap

A subtle but critical problem: the training system (YOLO) and inference system (SGLang) use different GPU kernels, scheduling strategies, and parallelism. Even tiny per-token probability differences compound across 128k-token rollouts and can destabilize training.

The fix: use BF16Brain Float 16 — a 16-bit number format that preserves the range of FP32 (same exponent size) but with reduced precision. More numerically stable than FP8 for RL, where small probability differences compound across long sequences.Learn more for both learner and inference (not lower precision), plus MoE routing replay and top-p mask replay to ensure both systems make identical routing and sampling decisions.

The numerics gap between inference and training is one of the most insidious sources of instability in large-scale RL. Before the BF16 fix, small discrepancies would accumulate over long rollouts and eventually cause the entire training run to diverge.

SWE Environment Build Infrastructure

Building the 265k SWE environments requires its own large-scale infrastructure. The build system is a two-pool RayAn open-source framework for distributed computing. Ray provides primitives (actors, tasks, object store) that make it easy to scale Python code across thousands of CPU/GPU cores. Used here for orchestrating environment builds across a large cluster.Learn more cluster running on approximately 30,000 CPU cores:

Main Pool

Handles work dispatching, Lance I/O, and pipeline state tracking. Lightweight and stateless — isolated from builder failures so orchestration is never disrupted.

Builder Pool

Runs the actual container builds. These are resource-intensive and failure-prone (disk exhaustion, OOM, build hangs). Builder pods are tagged with a Ray custom resource flag for exclusive scheduling. Credential isolation ensures builder pods executing untrusted Dockerfiles from open-source repos never hold credentials for internal services.

Build Architecture

Each builder pod contains two containers sharing NVMe-backed local storage:

  • Main container — Runs the Ray worker with rootless podmanA daemonless container engine for developing, managing, and running containers. Unlike Docker, podman runs without root privileges ("rootless"), improving security when executing untrusted code from open-source repositories.Learn more for loading built images and running grading containers
  • Sidecar container — Runs a rootless BuildKitA toolkit for converting source code to build artifacts (container images) efficiently. Supports layer caching, parallel builds, and OCI-compliant output. Used here because its layer caching dramatically reduces redundant work across same-repo problems.Learn more daemon for OCI image builds

The two containers communicate through the shared NVMe volume (BuildKit writes OCI tar archives that podman loads) and via localhost for the BuildKit control channel. This co-location avoids network transfer of large container images — the entire build-load-run cycle happens on local NVMe.

Caching and Throughput

The pipeline exploits BuildKit layer caching by grouping problems by repository and dispatching them to the same persistent Ray actor on a builder node. Since the actor persists across same-repo problems, shared base layers (apt-get install, pip install, dependency compilation) are built once and reused.

Weight Transfer

Every few training steps, updated model weights must be transferred from the learner (768 GPUs) to the inference fleet (4,096 GPUs). This is a distributed synchronization problem because the two systems shard the model differently.

Rocket compiles a transfer plan once at job start that maps each parameter sub-shard from learner ranks to inference ranks, including any necessary dtype casts or layout changes. The plan reuses across weight updates and handles replicas joining, leaving, or being replaced at runtime.
