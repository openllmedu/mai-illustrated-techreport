STEM Climb

Training the STEM specialist: 5 million verified problems across math, science, and competitive coding.

TL;DR

The STEM climb uses 5M+ verified problems spanning math, physics, chemistry, and 160k competitive coding problems in 17 languages. A four-phase pipeline extracts (question, answer) pairs from raw documents, verifies them, and scores difficulty. Three-stage deduplication ensures no benchmark contamination.

Overview

The STEM climb is the longest of the three specialist RL runs. It covers mathematics, physics, chemistry, and competitive programming. The goal: teach the model to solve hard, single-turn reasoning problems where the answer can be verified automatically.

Every problem in STEM training has a verifiable answer — either a ground-truth value (checked with SymPy or an AI judge) or a set of test cases (for code). This is what makes RL possible: the model generates an answer, and the system can objectively say whether it's right or wrong.

The STEM Data Pipeline

Building 5 million verified math/science problems from raw documents is a major engineering effort. The pipeline has four phases:

Figure 17 — STEM PDF Processing Pipeline

The pipeline transforms textbooks and academic PDFs into verified (question, answer) pairs through four phases: parsing, pairing, curation, and scoring.

Phase 1: Hierarchical Parsing

Raw documents (textbooks, academic PDFs) go through OCROptical Character Recognition — converting images of text (scanned pages, PDF renders) into machine-readable text. For STEM documents, this is especially challenging because of mathematical notation, tables, and figures.Learn more using vision-language models. The system builds a hierarchical document structure, resolves broken cross-references (e.g., "see Problem 3.5" when Problem 3.5 is on a different page), and extracts candidate question-answer pairs.

Phase 2: QA Pairing

Many textbooks put exercises and answers in separate locations (end of chapter, appendix, etc.). A multi-round matching stage uses structural signals and semantic similarity to link each question to its correct answer. An LLM validates each proposed pairing.

Phase 3: Curation

Each (question, answer) pair goes through multiple quality filters:

  • Verifiability check — Can the answer be objectively verified? Open-ended discussions are dropped.
  • Question type classification — Is it open-ended, multiple-choice, or a proof?
  • Taxonomy assignment — Fine-grained STEM topic tags (e.g., "differential equations > second-order linear")
  • PIIPersonally Identifiable Information — names, email addresses, phone numbers, etc. A classifier flags any PII, and flagged items are dropped.Learn more detection — Remove any items containing personal information
  • Answer leakage — Drop items where the answer is trivially contained in the question
  • Conversion — Multiple-choice questions are rewritten as open-ended (multiple-choice can be solved by guessing). Proofs are converted to verifiable form. This step runs 3 times with consensus voting.

Phase 4: Scoring

Each problem is solved k times by each of four model tiers of increasing strength. The pass rates group items into difficulty brackets. A blind-grading stage catches faulty ground truths: when the strongest model consistently disagrees with the provided answer, the item is reviewed and potentially dropped.

How blind grading catches bad answers: A calculus problem claims the answer is "3.14". The strongest model tier solves it 5 times and gets "pi" (approximately 3.14159) every time. The grader compares the model's consensus answer against the provided "3.14" — since the model's answer is more precise, a judge reviews and corrects the ground truth.

Competitive Coding Data

Coding problems need test cases, not just answers. The team uses a separate pipeline with targeted sources (coding competition archives, vendor-acquired data) rather than extracting from PDFs.

Each problem includes reference solutions verified against test suites, runtime/memory constraints, and supports 17 programming languages (Python, C++, Java, Rust, TypeScript, etc.). The dataset covers algorithms like dynamic programming, graph traversal, divide-and-conquer, and search.

Deduplication & Decontamination

All STEM data is deduplicatedRemoving duplicate or near-duplicate items from the training data. Critical for RL: if the same problem appears multiple times, the model overfits to those specific problems rather than learning general reasoning strategies.Learn more against benchmarks using a three-stage pipeline:

  1. Exact dedup — SHA-256 hashes catch identical questions
  2. Lexical fuzzy dedup — Character n-gram shingling + MinHash LSHLocality-Sensitive Hashing with MinHash — a technique for efficiently finding near-duplicate documents. Instead of comparing every pair (which would take O(n^2) time), MinHash creates compact "signatures" that can be compared quickly. Documents with similar signatures are likely near-duplicates.Learn more finds near-duplicates
  3. Vector dedup — Embedding-based cosine similarity catches semantically similar problems
The hyperparameters at each deduplication stage are carefully tuned to retain maximum data while ensuring zero benchmark leakage — the team wants high scores to reflect genuine reasoning ability, not memorization.

How Reasoning Traces Evolve

Because MAI-Thinking-1 climbs from scratch without distilling on any third-party chain-of-thoughts, the team has a clean vantage point for studying how reasoning behavior changes as the model strengthens during RL training. Three distinct behavioral archetypes emerge:

Weak Models Guess, Strong Models Work Hard

On an AIME 2024 problem (answer: 240), both weak and strong checkpoints derive the same algebraic candidates k ∈ {'}8, 32, 200, 512{'}, but they diverge at the critical verification step:

Weak model: Guesses candidate minimizers from the visible roots 18, 72, 98, producing spurious values like k = 40 and k = 152. It skips domain checking entirely, arriving at the wrong answer (704).
Strong model: Checks each candidate systematically — for k = 512, it computes the quadratic roots and finds one is negative (x ≈ -21.70 < 0), correctly excluding it. It then verifies no other equality points exist, arriving at the correct sum: 8 + 32 + 200 = 240.

Weak Models Brute Force, Strong Models Find Invariants

On an AIME 2025 number theory problem about cubes modulo 37:

Weak model: Assumes cubing is a bijection on units mod 37, which would simplify the cubic condition to a linear one. But this is false: gcd(3, φ(37)) = 3, not 1. The incorrect linearization leads to a wrong answer.
Strong model: Identifies the relevant structural invariant — unit cubes form an index-3 subgroup characterized by congruence to ±1 (mod 9). It traces the full group structure of (ℤ/3eℤ)* ≅ C2 × C3e-1 and uses this to count solutions correctly.

Strong Models Are Skeptics

On another AIME 2025 problem, the strong model pauses to re-examine its own solution when uncertain:

Weak model: Labels an empty grid as "maximal" and never rechecks, producing a count of 1024.
Strong model: Distrusts its own converse argument — "Wait, let's re-examine" — and tests it on a small 1×1 case. The small-case test reveals the error and lets the model correct its logic before answering.
The evolution from weak to strong reasoning is not about learning more facts — it's about learning to verify, to find structural invariants instead of brute-forcing, and to distrust one's own initial conclusions.
