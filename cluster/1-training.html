Section 6.1

Training Cluster & Stability

How 8,000 GPUs were organized, monitored, and kept productive for frontier-scale training.

TL;DR

MAI-Base-1 trained on 8K GB200 GPUs at a single site, achieving 90.0% goodput with only 51 hours of total overhead. The team optimized for usable capacity (not peak FLOPs), tracked both visible failures and silent efficiency losses, and treated determinism as a first-class infrastructure property to ensure reproducibility across restarts.

The Training Cluster

MAI-Base-1 was trained on a single logical cluster at one site with 8,000 GB200NVIDIA GB200 — a high-end GPU based on the Blackwell architecture. Each chip has significantly more memory and compute than the previous-generation H100. Used for MAI-Base-1 pre-training.Learn more GPUs. The team deliberately kept training on one site with one GPU generation to reduce experimental variance — homogeneous hardware means consistent performance characteristics and fewer confounding variables.

The planning target was not raw peak performance but usable training capacity: the fraction of delivered hardware that could be scheduled, kept healthy, driven at high MFUModel FLOP Utilization — the fraction of theoretical peak compute that is actually used for useful training operations. An MFU of 50% means half the GPU's compute capability is used for forward/backward passes; the rest is lost to communication, memory movement, and idle time.Learn more, and recovered quickly after failures.

Why "usable capacity" matters more than peak FLOPs: An 8,000-GPU cluster with 100% theoretical FLOPs that crashes every 2 hours (requiring 30 minutes to restart + recompute from the last checkpoint) delivers far less useful training than one with 85% peak FLOPs that runs stably for days. The team optimized for the latter.

GPU Architecture Basics

Each GB200 GPU contains thousands of small compute units organized into Streaming MultiprocessorsThe fundamental compute unit of an NVIDIA GPU. Each SM contains 128 CUDA cores for general math, 4 Tensor Cores for matrix multiplication, shared memory, and a register file. A GB200 has ~132 SMs.Learn more (SMs), each with dedicated Tensor CoresSpecialized hardware for matrix multiplication — the core operation in Transformer training. Tensor Cores process large matrix tiles in a single operation, providing massive throughput for the linear algebra that dominates LLM training.Learn more for matrix math. The memory hierarchy determines actual performance:

  • Registers (~33 MB total) — fastest, within each SM
  • SRAM / L1 Cache (~33 MB total) — on-chip, used by FlashAttentionAn algorithm that reorders attention computation to keep data in fast on-chip SRAM instead of reading/writing slow HBM repeatedly. Runs 2-4x faster with much less memory. Used by MAI via FlashAttention-4.Learn more
  • L2 Cache (~50 MB) — shared across all SMs
  • HBM (VRAM) (~192 GB, ~8 TB/s) — main GPU memory, where model weights live

The memory bandwidth bottleneck: LLM training (especially at batch=1 during inference) is almost always limited by how fast data can be read from HBM, not by compute capacity. Each weight is loaded from HBM and used for just 2 FLOPs (one multiply + one add). The Tensor Cores can do thousands of TFLOPS, but they sit mostly idle waiting for data to arrive from HBM. This is why:

  • Batching is critical — it amortizes HBM reads across multiple inputs, increasing useful FLOPs per byte loaded
  • Quantization (FP8, INT4) reduces bytes loaded per weight, improving arithmetic intensity
  • NVIDIA's recent GPU generations have focused on increasing bandwidth: A100 (2.0 TB/s) → H100 (3.35 TB/s, +68%) → H200 (4.8 TB/s, +43%) → B200 (8.0 TB/s, +67%)

Training Stability & Determinism

At 8,000 GPU scale, failures are routine: node crashes, InfiniBandA high-speed networking standard used to connect GPUs across servers in a cluster. Much faster than Ethernet for the all-reduce and all-to-all communication patterns that distributed training requires. Link "flaps" (temporary disconnections) can silently degrade performance.Learn more link flaps, out-of-memory errors, and checkpoint stalls. The team tracked both visible failures (crashes, OOM, pod terminations) and silent efficiency losses (MFU degradation, slow scheduling, memory pressure).

Deterministic Training

DeterminismThe property that running the same training with the same data on the same hardware produces exactly the same model. At frontier scale, this requires eliminating silent data corruption, keeping communication topology stable, and preserving the order of floating-point operations across checkpoint/restart boundaries.Learn more was treated as a first-class infrastructure property. It depends on:

  • Eliminating silent data corruptionHardware errors where a GPU produces incorrect results without signaling an error. These are rare but devastating — a single corrupted gradient update can subtly degrade the model with no obvious symptom until much later.Learn more in GPUs
  • Keeping communication topology stable
  • Preventing unhealthy devices from entering the training job
  • Preserving the order of floating-point operations across restarts

Goodput: The Primary KPI

GoodputThe ratio of ideal training duration to actual wall-clock duration. If training should theoretically take 100 hours but actually takes 110 hours (due to failures, restarts, and overhead), goodput is 100/110 = 90.9%. The gap is decomposed into overhead categories to identify what's eating into useful training time.Learn more measures how much of the allocated GPU time translates into actual training progress. The pre-training run achieved 90.0% goodput at 8K GPUs.

The improvement pattern followed two layers: first reducing visible failures (crashes, requeues, OOM), then eliminating silent goodput loss (MFU drops from network degradation, memory pressure, checkpoint stalls). The second layer is harder because the job keeps running — it just runs slower.
At frontier scale, every hour of overhead compounds across thousands of GPUs. The operating goal: every failure mode, runtime slowdown, and MFU regression has an owner, a detection signal, and a quantified impact on usable FLOPs.

Hardware and Cluster Architecture

MAI-Thinking-1 was developed on a heterogeneous accelerator fleet spanning NVIDIA H100, GB200, and GB300 systems. The main pre-training run was placed on a single GB200 cluster at one site. GB200 and GB300 clusters are provisioned as rack-scale NVL72An NVIDIA rack-scale unit containing 72 GPUs connected by NVLink for high-bandwidth scale-up communication. Within the rack, GPUs can communicate at ~900 GB/s; between racks, InfiniBand provides lower-bandwidth scale-out communication.Learn more units, with each rack providing a 72-GPU NVLink domain for high-bandwidth scale-up communication, while inter-rack RDMA uses InfiniBand.

Each site is partitioned into Kubernetes clusters (typically one per datacenter building). Topology labels are assigned using the physical host identity — rack, host, and locality — and consumed by scheduling to ensure jobs land on topologically appropriate capacity, not just any available GPUs.

Cluster Certification

At thousands of GPUs, failures are expected. Certification serves as the first reliability boundary — preventing bad nodes, degraded links, marginal storage, and silent-corruption risks from entering the production training pool. The framework is automated, Kubernetes-native, and hierarchical:

Single-Node Diagnostics

Extended stress tests on GPUs, CPU cores, HCAs, NVLink links, and main memory. Isolates high ECC rates, irregular throttle behavior, GPU clock violations, link flaps, and other marginal conditions before admitting the node to production.

Rack-Level Collectives

NCCL collectives stress both intra-node and inter-node communication paths per rack. These tests were instrumental in stabilizing the GB200 and GB300 racks — multiple racks were found with fewer than 16 healthy nodes and excluded from large training runs.

Cross-Rack InfiniBand

Exercises fabric paths that single-node and rack-level tests cannot cover. Groups nodes across racks, rails, and leaf groups to validate spine-layer behavior, path diversity, and cross-rack RDMA performance. Run on demand during bring-up and incident investigation.

New nodes and remediated nodes follow the same path. Nodes returning from repair must pass certification again, preventing repeat offenders from cycling back into large training jobs.

Node Lifecycle

Certification is one stage in a closed-loop node lifecycle:

From initialization through certification, production use, remediation, maintenance, and decommissioning. Runtime monitoring can move an Available node to Impaired when XID errors, ECC thresholds, NVLink degradation, InfiniBand link flaps, or storage faults are detected.

A new or remediated node enters Init (tainted, initialized, labeled, configured). The certification controller runs the tiered test suite. Passing nodes become Available; failing nodes become Impaired. Transient issues enter Auto Remediation (reboot, soft drain). Persistent hardware issues route through Guest Health Reporting to vendor maintenance. Unrecoverable nodes are decommissioned.

Scheduling and Orchestration

The scheduling stack is layered: Kubernetes maintains cluster state, KueueA Kubernetes-native job queueing system. Handles admission control, priority, quota enforcement, and preemption for batch workloads. In MAI's setup, Kueue also performs topology-aware placement to ensure large jobs land in compact topology regions.Learn more makes admission and quota decisions, MAI controllers maintain reservations and topology readiness, and Ray executes distributed jobs.

Rack Fragmentation Prevention

Small jobs from many queues can fill racks in a way that prevents later large jobs from acquiring contiguous capacity. The solution: soft rack reservations. Queues are assigned preferred racks, and workloads land on those racks first. Borrowing is possible when capacity is idle, but reclaimWithinCohort lets a queue reclaim its reserved racks when needed — improving bin packing under load while preserving utilization during low demand.

Observability and Fleet Monitoring

The team combined low-level hardware telemetry, scheduler state, job metadata, and fleet-efficiency signals into a single operating view. GPU health was tracked through XIDs, ECC, thermals, power, clock throttling, NVLink state, NVLink bit-error rate, InfiniBand device state, local NVMe health, and PCIe errors.

Telemetry was stored across systems optimized for different time horizons:

SystemPurpose
DatadogNear-real-time metrics and log search
Azure Managed PrometheusIn-cluster and cross-cluster time-series collection
Azure Data ExplorerLong-retention analytical storage for logs, metrics, and cluster state

Alerting used the same layered model: local Prometheus rules for low-latency component failures, Datadog monitors for service signals, KQL-based checks for long-retention analysis, and Azure Monitor for resource alerts.

The unique design point: observability was part of the control loop. Hardware telemetry, fabric health, storage behavior, and scheduling state determined whether capacity was admitted, drained, remediated, or returned to service. The fleet was managed in terms of usable training capacity and goodput — not provisioned GPUs alone.
