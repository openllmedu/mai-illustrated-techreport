Section 2.8

YOLO: Distributed Training at Scale

You Only Launch Once — MAI's custom training framework built from scratch

TL;DR

YOLO is MAI's custom PyTorch-based framework providing custom FP8 kernels, 5 forms of parallelism (data/tensor/context/expert/pipeline), bitwise determinism (rare for large-scale training), and fault tolerance via async checkpointing with hot standbys. Over 20 optimizations were needed across 5 model versions to maintain >20% MFU on 8,192 GB200 GPUs.

YOLO (You Only Launch Once) is MAI's custom distributed training framework, built from scratch on PyTorch. It supports all training phases: pre-training, mid-training, SFT, and RL.

Five Forms of Parallelism

Data Parallelism (ZeROZero Redundancy Optimizer — a technique that eliminates memory redundancy across GPUs. Stage 1 shards optimizer state, Stage 2 adds gradients, Stage 3 adds parameters. Each stage saves more memory but requires more communication.Learn more 1-3)

Splits optimizer state, gradients, and/or parameters across GPUs. Custom implementation stores parameters in sharded form regardless of ZeRO stage, simplifying distributed AdamW. Parameters grouped by sharding type and data type to minimize the number of collective operations.

Example: With 128 data-parallel GPUs, the optimizer state for a 1T-parameter model (~16 TB in FP32) is split so each GPU stores only ~125 GB instead of the full 16 TB. Each GPU processes a different batch of text, computes gradients locally, then they synchronize. It's like 128 students each reading different chapters of a textbook and sharing their notes.

Tensor Parallelism

Splits weight matrices across GPUs via column-parallel and row-parallel GEMMs. Both weights and activations are sharded across the same ranks (sequence parallelism).

Context Parallelism

Ulysses-style: activation tensors are re-partitioned via all-to-all, moving the sharding from the sequence dimension to the attention-head dimension. Used for long-context mid-training (not pre-training).

Expert Parallelism

Distributes the 512 experts across GPUs within the NVLinkNVIDIA's high-bandwidth interconnect between GPUs. Much faster than PCIe — GB200 NVLink provides ~900 GB/s per GPU. GPUs connected by NVLink form a 'domain' (typically 8–16 GPUs per node) for fast local communication.Learn more domain (EP=64). Dropless routing uses variable-size all-to-all communication. A static-memory mode runs multiple capped rounds per expert group to prevent imbalance-induced OOMs.

Example: 512 experts ÷ 64 GPUs = 8 experts per GPU. When a token needs expert #347, it must be sent to GPU #43 (which hosts experts 344–351). In a batch of 134M tokens, each expert might receive anywhere from 100K to 500K tokens depending on routing — this variable workload is why "dropless" routing and static-memory capping exist.

Pipeline Parallelism

Splits the model vertically across stages. Available but not the primary parallelism mode for MAI-Base-1 pre-training.

Bitwise Determinism

Two training runs with the same hardware resources and configurations will produce bitwise identical models.

This is unusual — most frameworks sacrifice determinism for speed. It requires:

  • Deterministic data pipelines — fixed micro-batch ordering across runs and restarts
  • Complete checkpoints — model weights, optimizer state, FP8 scaling history, dataloader progress, RNG seeds
  • Deterministic GPU kernels — fixed reduction orders (no unordered atomics), tiled accumulations, stable sort for MoE routing
  • Deterministic network collectives — NVLink SHARP disabled, consistent NCCLNVIDIA Collective Communications Library — handles multi-GPU communication primitives (all-reduce, all-to-all, broadcast). The de facto standard for distributed deep learning on NVIDIA GPUs.Learn more topologies
Why is this hard? When 8,192 GPUs add up numbers, the order of additions affects the result due to floating-point rounding. Adding 0.1 + 0.2 + 0.3 gives a different bit pattern than 0.3 + 0.2 + 0.1 in floating-point. Normally GPUs add in whatever order finishes first (non-deterministic). YOLO forces a fixed addition order, sacrificing some speed for perfect reproducibility — so if a training run crashes and restarts from a checkpoint, it produces the exact same model as if the crash never happened.

Golden configurations track historical loss metrics; any numerical change creates an explicit entry in the software history.

Fault Tolerance

At 8,192 GPUs, hardware failures are frequent. YOLO minimizes lost training progress through:

How frequent? With 8,192 GPUs running 24/7, component failures (GPU memory errors, NVLink faults, power supply glitches) happen multiple times per day. A single GPU failure halts all 8,192 GPUs until training can resume. Without fast recovery, you might lose hours of training per day — and at this scale, each hour of compute costs roughly the equivalent of a luxury car.
  • Distributed checkpointing — rewrote PyTorch DCP, reducing CPU memory and save time by >10x. Pre-computed save plans cached in persistent storage.
  • Asynchronous checkpointing — device→host copy in training processes, then offload to a separate process that writes to storage while training continues.
  • Hot standbys via Ray actors — in-job restarts without pod recreation. OS caches explicitly cleared on GB200 to prevent crash loops from residual GPU memory.
  • Local Azure Blob Storage — low-latency access eliminates need for node-local caches. Replicated state broadcast via NCCL to avoid storage hotspots.
