Pre-training Data

30 trillion tokens from web, code, books, and academic papers — sources, governance, and processing

TL;DR

MAI-Base-1 was trained on 30T tokens from four in-house sources: web (HTML + PDFs), public GitHub code, books/journals, and academic papers. No synthetic data, no open-source training datasets. Code dominates at 54.6% of the mix. All data goes through multi-stage filtering, quality scoring, and 5-layer deduplication. Math is so scarce (300B tokens) it's repeated 5.28x on average.

All pre-training data was built in-house from four base sources. No open-source training datasets, no AI-generated (syntheticData generated by AI models rather than written by humans. While synthetic data can augment training, it risks introducing model biases, hallucinated facts, and distributional artifacts. MAI chose to use only human-authored data for pre-training.Learn more) content. Data quality, not just quantity, consistently proved more important for both pre-training metrics and downstream reasoning.

Key observations:

  • Code dominates at 54.6% of training — reflects the model's target use cases
  • Math data is scarce (only 300B unique tokens) but so valuable it's repeated 5.28x on average
  • Web text and PDFs are abundant — seen less than once on average (0.55x and 0.53x)
  • Multilingual is heavily downsampled — 8.1T available but only 0.5T used (0.06x)
What does 5.28x epochs mean? The model has only 300B unique math tokens but needs 1.6T math tokens in its training budget. So every proof, worked solution, and equation derivation is shown to the model ~5.3 times across training. Meanwhile, from 8.1T available web tokens, only 4.5T are used (0.55x) — more than half the web text is never seen even once. This reflects the scarcity premium: high-quality mathematical reasoning data is genuinely rare on the internet, so it's worth repeating.

HTML Extraction

Extracting trainable text from web HTML is surprisingly tricky — math, code, and tables are often lost by off-the-shelf tools. Four different extraction methods are used depending on the source:

  • Source-specific parsers — for standardized formats (HTML, XML)
  • Hand-crafted extractors — using BeautifulSoup for domains with consistent structure
  • LLM-based processing — for targeted extraction where heuristics fail (restricted to keep/remove decisions, cannot add synthetic content)
  • Raw content training — e.g., training directly on Wikipedia wikitext markup (3x more verbose but preserves infoboxes and structure better)
Example — why extraction matters: A web page about the quadratic formula might render beautifully in a browser: x = (-b +/- sqrt(b^2-4ac)) / 2a. But a naive HTML extractor might output: x = (b b24ac) / 2a — the minus signs, square root, and superscripts are lost because they were encoded as MathML or embedded in SVG. The custom STEM extraction pipeline preserves the LaTeX: x = \frac{-b \pm \sqrt{b^2-4ac}}{2a}, which the model can actually learn from.

Tokenization

Before any text enters the model, it must be converted to tokens — numbered pieces the model can process. MAI-Base-1 uses the o200k_base tokenizer with a vocabulary of 200,019 tokens, based on Byte-level BPE (Byte Pair Encoding).

How BPE works: Start with the 256 possible byte values as the base vocabulary. Then iteratively find the most frequently adjacent pair of tokens in the training corpus and merge them into a single new token. Repeat until the vocabulary reaches the target size. Common English words like "the" become single tokens; rare words are split into subword pieces; any text in any language or script can be encoded because bytes cover everything.

Why token counts differ from word counts: Common English text is efficient — "The cat sat on the mat" uses ~6 tokens (~1 per word). But JSON like {"user_id": "abc123"} might use ~10 tokens because punctuation, underscores, and quotes each consume tokens. CJK characters often use 2-3 tokens each. Code with deep indentation burns tokens on whitespace. This is why the report measures data in tokens, not words — the same "amount of text" can cost very different numbers of tokens depending on content type.

Filtering & Categorization

After extraction, data goes through multi-stage filtering and categorization using five classes of techniques:

  • Metadata signals — domain names, file paths, PDF creator/producer fields
  • Heuristics — word count, digit ratio, duplicate-line fraction, stop-word density
  • Learned classifiers — fastTextA fast, lightweight text classification library developed by Meta. Uses bag-of-word-n-grams with subword features. Much faster than LLM-based classifiers, making it practical for filtering billions of documents.Learn more and embedding-based models for language, topic, quality, educational level
  • Prompted LLMs — for nuanced decisions like quality judging and topic labeling
  • Manual exploration — to identify failure modes and build training data for classifiers

This produces interpretable data "buckets" (quality tiers, languages, topics, educational levels) that enable controlled experiments during data mixture optimization.

Careful, multi-layered data processing — not just scale — was the key differentiator. Rigorous deduplication and quality filtering consistently improved both pre-training metrics and downstream reasoning benchmarks.
