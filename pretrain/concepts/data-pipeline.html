Data Processing Pipeline

How 1.2 trillion web pages become high-quality training data — the full pipeline from crawl to corpus

TL;DR

MAI processes data from four major sources — web HTML, web PDFs, books/journals, and public GitHub — each with its own dedicated pipeline. Web data alone starts at 1.2 trillion pages and is filtered, extracted, deduplicated, and categorized down to the final training corpus. No synthetic data is used anywhere.

Figure 4 — Web HTML Pipeline

The processing flow for web HTML data: proprietary crawl + Common Crawl → HTML extraction → filtering → exact + fuzzy dedup → cross-source dedup → embeddings → specialized pipelines for general web, STEM, code, and key domains.

Web HTML (Largest Source)

Crawling & Extraction

  • ~1.2 trillion pages crawled from a proprietary crawler + Common Crawl (~300B pages, deduplicated to latest version per URL → 100B)
  • HTML converted to text using TrafilaturaAn open-source HTML extraction library. Handles encoding detection, language identification, and main-content extraction. Used as the default extractor, with custom alternatives for STEM content where Trafilatura drops math/code.Learn more with encoding inference (not assuming UTF-8)
  • AI-content detection model removes domains with extensive AI-generated content

Specialized Sub-Pipelines

General Web Pages

Embedding-based attribute models score educational value, factual accuracy, writing quality, information density, reasoning content, and general-knowledge value. Bottom 70% of English documents filtered. Then Gopher-style heuristic filters (word statistics, punctuation, common n-grams). Yields ~7.4B English documents. Additionally, a curated subset of human-selected long-form content from magazine aggregators and social platform reference links.

STEM Pages

Identified via 7 binary topic classifiers (Math, Physics, Statistics, Chemistry, Biology, Engineering, CS) plus educational-value and educational-level classifiers. Custom extraction pipeline preserves MathML/LaTeX and code blocks (Trafilatura often drops these). LLM-based section classification (keep/remove only, cannot add content). Yields 680B English STEM tokens (76B math) + 760B multilingual STEM tokens.

Code Pages

Reuses STEM pipeline filtering on Computer Science topic. Each document scored by Qwen3-30B with a judge prompt optimized using GEPA/DSPy against ~2,000 human labels. Yields ~233B tokens.

Web PDFs

  • ~10B PDFs collected, filtered to 620M for OCR processing
  • Converted using Azure Document Intelligence (Azure DI)
  • Post-processing: equation/table normalization, boilerplate removal (headers/footers/figure text), OCR artifact cleaning, line unwrapping, reference section removal
  • SEO/spam filtered using text classifiers + PDF metadata (creator/producer fields are high-precision signals)
  • After fuzzy dedup: 1.8T English + 1.85T multilingual tokens
  • Categorized as educational/non-educational, with educational split into math/CS/STEM/non-STEM and assigned high school/undergrad/graduate level

Books & Journals

  • Acquired from publishers through commercial agreements
  • Dedicated ingestion pipeline per provider (formats vary)
  • Processing: OCR artifact cleaning → heuristic filtering → content selection → exact/title/fuzzy dedup
  • LLM-annotated topic and quality labels for data mixing control

Public GitHub Code

7.4T tokens organized into three datasets:

Files (1.26T tokens)

Latest version of each file across all repos. Grouped by repo, sorted in depth-first traversal order, concatenated into repo-level sequences. Heuristic filtering similar to StarCoder2.

Commits (4.5T tokens)

Most recent 10K commits per repo. Each contains pre-commit file state (loss-masked prefix) + commit patch (trainable). Commits that appear in PRs are removed to avoid redundancy. Patches rendered in git-diff or search-and-replace format.

What a training example looks like: The model sees the file before the change (masked — it doesn't train on this, just uses it as context), then the diff: - old_value = x * 2 / + new_value = x * 2 + bias, plus the commit message: "fix: add bias term to linear transform". This teaches the model to understand code changes in context — not just what code looks like, but how and why it evolves.

Pull Requests (1.19T tokens)

Full PR context: title, body, linked issues, reviews, threads, comments, file states, constituent commits. Decontaminated against SWE-bench Verified. Review comments placed after corresponding commit patches. Prefix compression for long PRs (>256K tokens discarded).

Shared processing across all three: junk folder removal (node_modules, build, etc.), generated code detection (_pb2.py, .d.ts), binary/image/archive exclusion, 30K character limit, character-composition checks, SHA-512 exact dedup, MinHash LSH fuzzy dedup, semantic dedup via Qwen3-Embedding-0.6B, decontamination against reasoning training/evaluation data, quality scoring and binning.
