Mixture of Experts (MoE)

How MAI-Base-1 achieves 1T-parameter knowledge with 35B-parameter compute cost

TL;DR

MoE models have many "expert" sub-networks but only activate a few per token, achieving the knowledge capacity of a huge model with the compute cost of a small one. MAI-Base-1 has 512 experts, activates 8 per token, and uses LatentMoE compression to reduce communication overhead.

What Problem Does MoE Solve?

There's a tension in AI model design: bigger models know more, but bigger models cost more to run. A 1-trillion-parameter dense model would be incredibly knowledgeable but prohibitively expensive for every inference.

MoE resolves this by making the model conditionally large. The full 1T parameters store knowledge, but only 35B are actually computed for each token. The routerA small network that looks at each token and decides which experts should process it. In MAI-Base-1, it's a learned softmax gating function that selects the top-8 experts out of 512.Learn more decides which experts to activate based on the input.

A dense 1T-parameter model would run all 1 trillion parameters for every token — even the word "the." With MoE, "the" activates only 35B parameters (8 out of 512 experts), using 3.5% of the total model. The other 96.5% sit idle for that token. A different token — say a rare chemistry formula — activates a completely different set of 8 experts, accessing knowledge stored in a different slice of the 1T parameter space. Same total knowledge, 28x less compute per token.

How MAI-Base-1's MoE Works

1. Token arrives at an MoE layer

The token's representation (a vector of numbers) enters the MoE layer after being processed by attention.

2. Router selects experts

The router network computes a score for each of the 512 experts using the full-sized token representation. The top-8 scoring experts are selected via softmaxA mathematical function that converts a list of raw scores into probabilities that sum to 1. In MoE routing, softmax turns expert scores [2.1, 0.5, 3.7, ...] into probabilities [0.15, 0.03, 0.42, ...], then the top-8 highest probabilities determine which experts are used.Learn more gating.

Example: The token "eigenvalue" arrives. The router scores all 512 experts and finds that experts #12 (linear algebra), #87 (numerical methods), #203 (physics), #341 (differential equations), and four others score highest. These 8 experts process the token, each contributing their specialized knowledge. Meanwhile, experts focused on cooking recipes, legal contracts, or Python web frameworks score low and sit this one out.

3. LatentMoE compression

Before the token is sent to its selected experts (which may be on different GPUs), it's compressed to half size via a shared down-projection matrix. This is the "latent" in LatentMoE — tokens travel in a compressed latent space, cutting all-to-all communication volume in half.

4. Expert computation

Each of the 8 selected experts processes the compressed token independently using a SwiGLUSwish-Gated Linear Unit — a type of activation function that multiplies a swish activation with a linear gate. Empirically better than ReLU for Transformer FFNs.Learn more feed-forward network. The expert expands the compressed representation by 3x, applies the non-linearity, then projects back down.

5. Combine and expand

The 8 expert outputs are combined (weighted by router scores), then projected back to full size via a shared up-projection.

Load Balancing

A critical challenge: if most tokens get routed to the same few experts, those experts become bottlenecks while others sit idle. MAI-Base-1 uses:

Example of the problem: Suppose 80% of tokens in a coding-heavy batch all route to the same 20 "code experts." Those 20 experts are overwhelmed with 10x the expected load. The other 492 experts have almost nothing to do. GPU memory spikes on the machines hosting the popular experts (potentially causing out-of-memory crashes), while other GPUs sit idle. Load balancing ensures a more even distribution — each expert should get roughly 134M × 8/512 = ~2M tokens per batch.
  • Global-batch load balancing loss — expert frequencies are aggregated across all data-parallel workers and micro-batches within the same global batch (this aggregation strategy matters more than the specific loss type)
  • Fully dropless routing — no tokens are ever dropped. Variable-size all-to-all communication handles imbalanced loads. A static-memory mode runs multiple capped rounds to prevent OOM from extreme imbalance.
  • GShard-style loss — performs similarly to loss-free variants when global aggregation is ensured

Interleaved Layout

Instead of making every FFN layer an MoE (common approach), MAI alternates: MoE -> dense FFN -> MoE -> dense FFN. This interleaved layout:

  • Matches quality (sparsityThe fraction of total parameters that are NOT used for any given input. MAI-Base-1 has ~96.5% sparsity — only 35B of 962B parameters activate per token. Higher sparsity = more total knowledge stored with less per-token compute.Learn more EGFLOPs ≈ 1.0) of all-MoE architectures
  • Is ~20% faster in wall-clock time (EGTime advantage)
  • Doesn't benefit from shared experts (unlike all-MoE layouts which rely heavily on them)

MoE Failure Modes

MoE architectures introduce failure modes that dense models do not have. Understanding these explains why MAI-Base-1 invests heavily in load balancing and dropless routing:

  • Router collapse: The router learns to send most tokens to the same 1-2 experts, effectively reducing the model to a fraction of its capacity. The other 500+ experts are wasted. MAI-Base-1 prevents this with global-batch load balancing loss that penalizes uneven distributions.
  • Load imbalance: Even without full collapse, some experts may receive 10x the expected load while others sit idle. This causes GPU memory spikes on machines hosting popular experts (potentially OOM crashes) while other GPUs waste capacity. MAI's fully dropless routing with variable-size all-to-all communication handles this — a static-memory mode runs multiple capped rounds to prevent OOM from extreme spikes.
  • Quality issues as routing issues: When an MoE model produces a bad output, the root cause may be a routing decision (wrong expert selected) rather than expert quality. This makes debugging harder than with dense models.
  • Memory: all experts in memory: Even though only 8 of 512 experts activate per token, all 512 must be loaded in GPU memory. The total parameter count (~1T) determines memory needs, not the active count (35B). Expert parallelism across GPUs is required.
